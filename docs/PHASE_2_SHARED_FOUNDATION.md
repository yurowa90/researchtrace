# 사이트 분리 2단계: 공통 계정·권한·저장소 기반

현재 통합 사이트에 세 사이트가 함께 쓸 계정 연결과 저장소 기반을 추가했습니다. 학생·교사·관리자 전용 사이트 개설과 각 화면 구성은 후속 단계입니다. 사이트마다 로그인한 뒤 같은 학교 계정을 사용하는 구조이며, 여러 도메인의 브라우저 로그인 세션을 하나로 합치는 SSO는 아닙니다.

## 완료한 기능

| 기능 | 동작 |
| --- | --- |
| 공통 학교 계정 | 기존 `users.id`, 학생 ID, 학급 ID를 유지하며 `(siteId, subject)`를 학교 계정에 연결 |
| 기존 계정 보존 | 기준 사이트의 기존 로그인 식별자를 그대로 연결하며 기존 역할·승인 상태 유지 |
| 새 사이트 연결 | 이메일이나 사이트별 식별자 문자열이 같아도 관리자 확인 전에는 자료 접근 불가 |
| 관리자 승인 | 학교 설정에서 기존 승인 계정 선택, 본인 확인 근거 입력, 연결 승인·거절·해제 |
| 접근 차단 | 연결 해제 또는 학교 계정 정지 후 요청부터 차단. 원본·학생·분석 이력은 보존 |
| 처리 이력 | 처리자·시각·사유·연결 판본을 기록. 같은 판본에 대한 동시 승인은 덮어쓰기 차단 |
| 역할 검사 | 학생은 본인, 담임은 담당 학급, 관리자는 전체 범위. 추가 사이트 용도와 계정 역할도 서버에서 검사 |
| 공통 저장소 | 추가 사이트에 같은 Google 저장소의 서버 비밀 설정을 적용. 설정 누락·기준 학교 불일치 시 접속 중단 |
| 변경 요청 검증 | 브라우저 변경 요청의 출처를 검사하고 각 API에서 로그인·역할 권한을 별도 확인 |

사이트 계정 연결 승인과 신규 학교 계정의 역할 승인은 별도입니다. 기준 사이트의 신규 사용자는 승인 대기 학생 계정으로 등록되며, 자동 관리자 승격이나 이메일만으로 학생 기록 연결을 하지 않습니다. 기존 승인 대기 계정 관리 기능으로 학교 계정과 역할을 먼저 확정합니다. 추가 사이트에서 처음 온 사용자는 학교 계정을 새로 만들지 않고 연결 요청만 등록합니다.

## 관리자의 사용 순서

1. 기존 통합 사이트에서 학교 설정 → 자료 연결 점검과 원본 포함 전체 백업을 실행합니다.
2. 내 구글 저장소 연결에서 최신 개인 설치 코드로 Google 실행 권한 승인·웹 앱 배포·연결 확인·자료 복사를 완료합니다. 기존에 연결했다면 코드 교체와 `setupTrace` 재실행 후 웹 앱 배포를 갱신합니다.
3. 후속 단계에서 추가 사이트를 개설할 때, 소유자 관리자가 ‘추가 사이트 연결 설정’ 파일을 받아 서버 환경 변수로 설정합니다.
4. 사용자가 새 사이트에 로그인하면 공통 계정 연결 목록에 요청이 나타납니다.
5. 요청자의 본인을 확인하고 기존 학교 계정을 선택합니다. 확인 근거를 입력한 뒤 ‘학교 계정에 연결’을 누릅니다. 학생 계정과 학생 기록의 연결, 담임 학급 배정도 확인합니다.
6. 연결을 중단하려면 사유를 입력하고 ‘이 사이트 연결 해제’를 누릅니다. 현재 로그인에 쓰고 있는 본인의 연결은 이 화면에서 해제할 수 없습니다. 이전에 연결한 로그인은 같은 학교 계정에만 다시 연결할 수 있습니다.

## 서버 설정

| 설정 | 기준 통합 사이트 | 추가 사이트 |
| --- | --- | --- |
| `.openai/hosting.json`의 `project_id` | 현재 사이트의 고유 ID | 새로 발급된 해당 사이트의 고유 ID |
| `TRACE_PORTAL_MODE` | 기본값 `unified` | `student`, `teacher`, `admin` 중 용도에 맞는 값 |
| `TRACE_HOME_SITE_ID` | 통합 사이트에서는 생략 시 자기 ID | 기준 통합 사이트의 ID, 필수 |
| `TRACE_GOOGLE_LOCATIONS` | 소유자·폴더·시트 위치를 담은 기존 서버 설정 | 저장소 설치·이전을 하지 않으므로 불필요 |
| `TRACE_SHARED_GOOGLE_CONNECTION` | 기존 서버 DB의 연결 설정 사용 | 아래 형식의 JSON, 비밀 환경 변수로 필수 설정 |

```json
{
  "homeSiteId": "기준 사이트 ID",
  "endpoint": "https://script.google.com/macros/s/배포ID/exec",
  "secret": "기준 사이트가 발급한 연결 비밀키"
}
```

추가 사이트에는 별도 학교 데이터 DB를 만들거나 자료를 복사하지 않습니다. 기존 학교 데이터에 같은 서버 서명 키로 접근합니다. Google 서버는 서명·유효 시간·재전송·기준 학교를 확인하며, 각 사이트 서버는 중앙 학교 계정의 최신 역할과 연결 상태를 확인합니다. 추가 사이트의 소스는 각자의 Sites 프로젝트 식별자를 사용해야 합니다. 클라이언트가 전송한 `siteId`, 역할, 계정 ID를 로그인 근거로 사용하지 않습니다.

Google 전체 자료 변경은 기존 ScriptLock·판본 검사·Sheets 일괄 처리로 충돌을 차단합니다. 로그인 연결 생성은 충돌일 때만 최대 세 번 최신 자료로 재시도하며, 권한 변경과 일반 저장은 자동 재실행하지 않습니다.

## 자료 변경과 호환성

- 새 마이그레이션 `0006_site_identity_links.sql`은 `school_identities`, `identity_events`와 인덱스·이전 중 쓰기 금지 트리거를 추가합니다. 기존 학생·성적·원본 표를 삭제하거나 ID를 다시 만들지 않습니다.
- 공통 학교 자료는 1단계의 24개에서 26개 표로 늘어났습니다. 저장소 연결 비밀 설정은 학교 데이터 백업 대상에서 계속 제외합니다.
- 기존 Google 표의 행을 보존하며 빈 추가 표는 기존 무결성 해시와 호환됩니다. 구버전 Google 코드로 새 계정 연결을 저장하려 하면 갱신 안내를 반환합니다.
- 기존 계정의 학년·역할을 로그인만으로 자동 수정하던 동작을 제거했습니다. 로컬 가상 관리자 초기화는 개발용 로그인에만 남았습니다.

## 확인한 범위와 남은 운영 절차

자동 검증은 사이트별 계정 분리, 이메일 충돌, 신규 계정 승인 대기, 연결 해제, 학교 계정 정지, 역할 위조, 잘못된 사이트 역할, 동시 승인, Google 충돌 재시도, 변경 요청 출처, 마이그레이션과 데이터 보존을 포함합니다. 로컬 브라우저에서 가상 계정의 연결 승인·해제와 두 처리 이력을 확인했습니다. 기존 학생·교과·원본·분석 기능의 회귀 검증도 수행합니다.

이번 작업에서 운영 사이트의 Google 연결 설정 행은 아직 없었습니다. 서버 위치 정보가 비밀 환경 변수로 등록되어 있어도 실제 연결·자료 이전 완료와는 별개입니다. 소유자의 Google 실행 승인, 운영 원본 전체 백업과 이전 후 대조, 서로 다른 실제 Sites 세 곳에서의 로그인 검증은 아직 완료하지 않았습니다. 운영 사이트가 소유자 전용인 공개 범위도 유지합니다. 후속 사이트를 개설할 때 학교 사용자에게 맞는 사이트 접근 권한을 별도로 설정해야 합니다.

1단계 운영 백업 확인이 남은 상태에서 이번 변경은 기존 자료를 옮기지 않는 추가 표·계정 기반 구현까지만 적용합니다. 실제 Google 이전과 세 사이트 전환 전에 관리자 화면에서 백업을 생성·검증해야 합니다. Google 연결 안내와 이번 작업을 구분하여 완료 여부를 확인합니다.
